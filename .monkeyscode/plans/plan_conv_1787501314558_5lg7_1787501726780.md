# Cancellation & Penalty Business Logic Refactor (Option A)

## Context / What this resolves:

The current system has several issues with penalty/cancellation logic:
1. **Order creation blocking** uses `penaltyCount >= 3` — should use `penaltyAmount > 0`.
2. **`isPenalized`** boolean is redundant — `penaltyCount`/`penaltyAmount` are the source of truth.
3. **Flat 50 EGP penalty** — should be progressive: `50 + (penaltyCount * 10)`.
4. **Penalty accumulates** (`penaltyAmount += 50`) — should be assignment (`penaltyAmount = penaltyForCancellation`), representing only the current outstanding penalty.
5. **Stripe webhook** does NOT settle customer penalty on order payment.
6. **No independent penalty settlement** — settlement was embedded in order payment, creating a deadlock when order creation is blocked by `penaltyAmount > 0`.
7. **Penalty was added to new orders** — should NOT be, since customer is blocked until penalty is settled.

**Resolution (Option A):** Add independent penalty settlement endpoints (Stripe + Cash) so the customer can settle penalties without creating an order.

## Approach / Why this way:

- **Minimal architecture change**: Modify existing controllers in-place; add one new controller file + routes for penalty settlement.
- **Atomic MongoDB operations**: Use aggregation-pipeline updates for penalty calculation/settlement to prevent race conditions and negative values.
- **Progressive penalty**: `50 + (penaltyCount * 10)` calculated atomically in a single pipeline update.
- **No accumulation**: `penaltyAmount = penaltyForCancellation` (assignment, not `+=`).
- **Independent settlement**: New `POST /api/payments/penalty/create-intent` (Stripe) and `PATCH /api/payments/penalty/confirm-cash` (admin) endpoints. Webhook extended to handle penalty payments via metadata routing.
- **Idempotency**: Atomic `penaltyAmount > 0` condition prevents double settlement. Stripe PaymentIntent metadata routes webhook to penalty handler vs order handler.

## Phase 2: Cancellation Logic — Progressive Penalty + No Accumulation

**Goal:** Change customer penalty from flat 50 EGP accumulation to progressive non-accumulating assignment; remove `isPenalized`; use atomic operations.

**Files:**
- `HerfyBackend/controllers/orderController.js` (modify) — cancellation block (lines 331-358)

**Steps:**
1. Replace the customer penalty read-modify-write block with an atomic aggregation-pipeline update:
   ```js
   const updatedCustomer = await User.findByIdAndUpdate(
     order.customerId,
     [{
       $set: {
         penaltyAmount: { $add: [50, { $multiply: ["$penaltyCount", 10] }] },
         penaltyCount: { $add: ["$penaltyCount", 1] }
       }
     }],
     { new: true }
   );
   ```
   This calculates `50 + (currentPenaltyCount * 10)` and assigns it (no accumulation), then increments `penaltyCount` — all in one atomic operation.
2. Remove the `isPenalized = true` assignment.
3. Keep the tracking-expired exception (lines 332-338) unchanged.
4. Keep the handyman cancellation block (lines 287-329) unchanged — already correct.
5. Update the notification to use the returned `updatedCustomer` values.

**Risks:**
- Aggregation-pipeline updates require MongoDB 4.2+. Project uses transactions (requires 4.0+ replica set), so 4.2+ is safe.
- The `findByIdAndUpdate` with pipeline returns the updated document for notification.

## Phase 3: Order Creation Block + No Penalty on New Orders

**Goal:** Change block from `penaltyCount >= 3` to `penaltyAmount > 0`; don't add penalty to new orders; set `serviceAmount`.

**Files:**
- `HerfyBackend/controllers/orderController.js` (modify) — `createOrder` (lines 41-84) and accept logic (lines 410-413)

**Steps:**
1. In `createOrder` (line 41): Replace `customer.penaltyCount >= 3` with `customer.penaltyAmount > 0`. Update error message.
2. In `createOrder` (lines 68-84): Set `serviceAmount = finalPrice`, `penaltyAmount = 0` (since customer is blocked if > 0), `totalPrice = serviceAmount`. Add `serviceAmount` to `Order.create()`.
3. In `updateOrderStatus` accept logic (lines 410-413): When handyman sets price, also update `order.serviceAmount = price` and `order.totalPrice = price + (order.penaltyAmount || 0)`.

**Risks:**
- Customers with 1+ outstanding penalties are now blocked (previously only 3+). This is intended.
- Updating `totalPrice` at acceptance fixes stale Stripe charge amounts — correctness improvement.

## Phase 4: Existing Payment Settlement Fix

**Goal:** Fix cash payment settlement to set `penaltyAmount = 0` (not subtract); add penalty settlement to Stripe webhook for order payments; use atomic operations.

**Files:**
- `HerfyBackend/controllers/orderController.js` (modify) — `confirmCashPayment` (lines 792-798)
- `HerfyBackend/controllers/webhookController.js` (modify) — `payment_intent.succeeded` case

**Steps:**
1. In `confirmCashPayment`: Replace read-modify-write with atomic `findOneAndUpdate`:
   ```js
   if (order.penaltyAmount > 0) {
     await User.findOneAndUpdate(
       { _id: order.customerId, penaltyAmount: { $gt: 0 } },
       { $set: { penaltyAmount: 0 } }
     );
   }
   ```
2. In webhook `payment_intent.succeeded`: After marking order as paid, add penalty settlement (same atomic pattern). Also make the idempotency check atomic using `findOneAndUpdate` with `paymentStatus: { $ne: 'paid' }`.
3. Do NOT reset `penaltyCount` in either path.

**Risks:**
- The webhook restructure changes from "find-check-update" to "atomic find-and-update". Must distinguish "not found" from "already paid" for logging.

## Phase 5: New Penalty Settlement Endpoints (Option A)

**Goal:** Create independent penalty settlement via Stripe and Cash so customers can settle penalties without creating orders.

**Files:**
- `HerfyBackend/controllers/penaltyController.js` (create)
- `HerfyBackend/routes/paymentRoutes.js` (modify)
- `HerfyBackend/controllers/webhookController.js` (modify) — add penalty payment routing via metadata

**Steps:**
1. Create `penaltyController.js` with:
   - `createPenaltyPaymentIntent`: Customer-initiated. Reads `customer.penaltyAmount`. If 0, return 400. Creates Stripe PaymentIntent with `currency: "egp"`, `amount: penaltyAmount * 100`, `metadata: { type: 'penalty_settlement', userId }`. Returns `{ clientSecret, penaltyAmount }`.
   - `confirmPenaltyCashSettlement`: Admin-only. Body: `{ customerId }`. Atomically sets `penaltyAmount = 0` if `> 0`. Returns updated penalty info.
2. In `paymentRoutes.js`: Add:
   - `POST /penalty/create-intent` (auth, customer)
   - `PATCH /penalty/confirm-cash` (auth, admin only)
3. In `webhookController.js` `payment_intent.succeeded`: Before the order lookup, check `pi.metadata.type === 'penalty_settlement'`. If so, route to penalty settlement (atomic `penaltyAmount = 0` if `> 0`) and break. Otherwise, continue with order payment handling.

**Risks:**
- Stripe PaymentIntent metadata is limited to 40 key-value pairs and 500 chars per value — our metadata is tiny, no issue.
- The webhook must handle both penalty and order payments — metadata routing is the cleanest approach.
- Admin cash settlement requires trust — admin confirms cash was received. This is standard for cash flows.

## Conclusion

After all phases:
- `isPenalized` fully removed.
- Progressive penalty: 50/60/70/80... (no accumulation).
- Order creation blocked by `penaltyAmount > 0` (not `penaltyCount >= 3`).
- New orders have `penaltyAmount = 0` (no old penalty added).
- Independent penalty settlement via Stripe (new endpoint + webhook) and Cash (admin endpoint).
- `penaltyCount` never reset after payment; only `penaltyAmount` set to 0.
- All operations atomic; no negative values; no double settlement.
- Handyman logic unchanged (already correct).

## Warnings

- **Breaking change**: Customers with `penaltyAmount > 0` are now blocked from creating orders. They must use the new penalty settlement endpoints.
- **New endpoints**: `POST /api/payments/penalty/create-intent` and `PATCH /api/payments/penalty/confirm-cash` are new — frontend integration needed separately.
- **Webhook extended**: The Stripe webhook now handles both penalty and order payments via metadata routing. Existing order payment webhooks continue to work unchanged.
- **`totalPrice` updates at acceptance**: Orders where handyman's price differs from estimate now have correct `totalPrice` — affects Stripe charge amount (correctness fix).
